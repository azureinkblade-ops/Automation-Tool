## Existing Activation Contract

`ProductionActivation` (EA-4E.11, `tools/hermes_core/production_activation.py`) is the activation *object*: receiver, router/authority/transport/model bindings, `ENABLED`/`DISABLED`, canonical hash. `ProductionActivationValidator.validate` checks presence, ENABLED, receiver match, contract match, hash.

It does **not** carry request_id, governing_commit, issued_at, expires_at, nonce, issuer identity, operator intent, or single-use/claim/consume state.

`production_activation_explicit` on the app request is a boolean intent flag, not an authorization artifact.

`ProductionIssuancePolicy` currently issues execution authority and then builds ENABLED `ProductionActivation` in one policy. Tests inject that pair via `external_authority_and_activation`. That co-issuance is a qualified EA-4E.17 boundary and is not redesigned here.

A second artifact is justified because it adds request-scope, single-use, TTL, commit bind, and operator intent. It does not replace EA-4E.11 activation. Runtime continues to validate `ProductionActivation`. The new artifact only answers: may this request perform the activation transition (attach/accept ENABLED activation).

## Ordering

Issue is a dedicated operator action. It is not part of ordinary production submit and does not bind.

Claim, transition, and consume run inside the existing request lifecycle, after admission, so they cannot bypass the single slot.
